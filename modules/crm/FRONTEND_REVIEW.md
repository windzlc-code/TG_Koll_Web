# CRM 前端实施文档复核与补强记录

复核日期：2026-08-10

## 结论

附件描述的原生单页架构、统一登录、公共导航、固定浅色外壳、任务轮询、权限状态和人工接管已经具备，但附件把目标状态写成了“全部 10/10、零 TODO”，与当前代码不符。当前前端外壳已经可用，完整 CRM 业务页面仍需继续建设。

附件中的青绿色、深色主题和直接加载整份 `console.css` 的要求作废。CRM 继续使用公共固定浅色变量的灰蓝语义别名，不引入绿色，也不加载包含历史全局规则的巨大样式文件。

- 所有任务可查看步骤与证据时间线，动作机器码映射为简繁体名称。

## 第二轮工程核验（2026-08-10）

### 发布阻断：能力声明必须与真实闭环一致

- `customer_collection` 当前标记为 `adapted/enabled`，实际只创建 `collect_profile → browse_profile` 浏览任务，没有画像、热点、指定链接三种采集、去重、客户池生成和结果入库闭环。正式开放前应拆分为“主页浏览”和“客户采集”两个能力，或继续阻断完整采集能力。
- `threads_community_post` 当前只能把 `threads_group_invite_post` 转为普通 `publish_post`。页面名称应明确为“Threads 社群邀请帖”；Instagram Direct 建群、补充成员和成员验证继续保持阻断，不能用“群组运营已完成”表述。
- `templates_media`、`scheduling`、`analytics_tracking` 的后端基础存在，但前端分别只有只读列表、只读列表和无入口，不能标记为完整可用。
- `data_workspace` 仍缺池成员读写契约。数据库存在 `crm_pool_members`，但当前资源 API 和前端都没有客户池成员列表、标签、阶段、去重、批量增删及向触达流程交接的能力。

### 发布阻断：业务页面与服务端契约

- 十二个导航入口中仅总览、任务、账号为独立组件；采集、客户池、公开互动、私信、群组、关系、排程、模板和设置仍共用 `ResourceList`。入口存在不等于业务可完成。
- `outreach` 页面直接读取全部 `/tasks`，未按工作流类型筛选；`public` 页面读取全部事件，未形成公开互动批次视图。不同业务页面会展示不属于当前业务的数据。
- 通用资源只有列表和创建，没有详情、更新、停用或删除；因此客户池改名、标签维护、模板编辑、排程启停和目的地白名单管理都无法完成。
- 没有池成员专用 API，也没有模板版本/媒体引用、排程立即运行/重排/停止、关系验证及回复监控专用 API。
- 分析接口未被前端使用，且当前只返回工作流状态数和事件类型数，不足以呈现点击、送达、已读、回复、互动漏斗和趋势。

### 发布阻断：真实动作安全与接管

- 公开互动确认摘要仍是客户端输入回显，不是服务端预检。批量真实写操作必须先由服务端返回可执行数、重复数、策略拦截数、内容哈希、SKU、预计扣点和确认有效期。
- 任务创建接口用通用 truthiness 解释 `confirmed`；字符串 `"false"` 也会被当作已确认。服务端必须只接受严格布尔值，并校验与预检结果绑定的短期 Token，不能相信客户端自行提交的确认标志。
- 管理员代管工作区时，轮询得到 Kasm 会话后生成的首次跳转 URL 没有管理员工作区查询参数；浏览器页面跳转也无法携带 API Header，初次访问可能退回普通会话 Cookie 并返回 401/404。应使用后端签发的短期接管 URL，或在首次同源跳转中安全携带管理员上下文并换取短期 Ticket。
- 任务证据主区域仍只显示状态和“存在证据”，详情主要是原始 JSON。人工复核必须结构化展示平台、账号、目标、提交/确认时间、截图、平台链接、内容摘要、内容哈希和证据来源。

### 重要缺口：查询、后台和可靠性

- 列表 API 会静默忽略 `query/status` 等条件；前端只过滤当前已加载分页。已用 61 条数据验证：匹配记录位于第二页时，第一页会错误显示“无匹配结果”。正式大数据开放前必须实现服务端过滤和绑定过滤条件的游标。
- 后台已有全局策略、单用户授权、健康和导入，但仍缺文档要求的批量授权、客户池/任务/失败/导入统计，以及启停、授权、迁移和代管审计视图。
- 排程运行器存在，但创建契约未校验 Cron 和时区；无效表达式会静默回退为次日运行，用户无法识别配置错误。定时写动作会进入 `awaiting_confirmation`，而当前任务 UI 没有 `confirm` 操作，任务会永久停留；必须明确采用“创建排程时预授权固定快照”或“每次运行前确认”并补齐相应界面。
- 媒体上传只有写入和列表，没有受租户保护的内容读取、缩略图、下载和删除接口；也未限制图片像素/帧数或核对解码后的真实格式与扩展名/MIME，模板媒体仍不具备正式使用条件。
- CRM 自有错误已统一，但认证、参数校验和 CSRF 等框架错误仍可能返回 `detail`；前端当前不解析该结构，用户只会看到通用 HTTP 状态。应统一 CRM 路由异常适配并补充 `request_id`。
- 账号列表无分页；登录接管固定等待 30 秒，超时会关闭窗口但后台任务仍存在。应保留“继续等待/重新打开”入口，避免用户重复创建接管任务。
- `review_action` 路由存在重复导入和重复调用 `dispatch_next_action_atomic`。当前顺序执行保护可避免立即重复入队，但应删除重复路径并增加“复核后最多派发一个后继动作”的回归测试。

### 本轮验证结论

- 前端类型检查、11 项契约测试和 Vite 生产构建通过。
- CRM 后端、状态、导入及前端契约测试 46 项通过。
- 公共导航与登录回归 45 项通过，另有 33 个子测试通过。
- 生产 CRM JS/CSS 引用有效，禁用绿色和旧金色色值扫描为 0。
- 独立业务页面、跨页真实筛选、服务端预检和结构化证据验证失败。

因此当前状态是：原生容器、统一登录、权限外壳、任务状态机和固定浅色视觉基础可用；完整 CRM 业务迁移仍未达到正式开放标准，不能宣称“功能不缩水”或“10/10 完成”。
